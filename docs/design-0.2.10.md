# Design — v0.2.10, the index page

**Working document.** Started as seven questions; six are answered and recorded
under *Settled*, one is still open and is the only thing blocking the
implementation plan. When it closes, this becomes a roadmap section.

Everything here is measured against your base on **2026-09-01**, after v0.2.9
shipped. No records change in this release; the index is generated from what is
already in the graph.

---

A flat list of filename stems, no dates, no counts, no grouping, no filter.

## What there is to build with

Measured, not assumed.

**29 rows** — 24 `document` roots and 5 `session` roots. (Subagent transcripts
don't get rows; they render inside the tool call that launched them.)

**Titles are available.** Searching each document *depth-first* for its first
`Header`:

| filename stem shown today | title from the first Header |
|---|---|
| `changelog` | CHANGELOG |
| `claude` | compost — start here |
| `readme` | compost — conversations to an addressable wiki |
| `todo` | TODO |
| `019fe816-e1ce-7a60-9643-edf50fdd80ee` | Bring back graph database as the main storage |
| `7e56302e-54c2-46a1-929c-5e37b2102001` | Where things stand |
| `a7aca92b-54bf-44f6-8851-35eff9d48eb4` | What this is |

**17 of 24** documents yield a title this way. Six more yield a usable first
line (*"In theory the repo is self explanatory if you…"*). **One yields
nothing** — its first three blocks are a slash command that arrived as code
blocks — and would fall through to its uuid filename.

*Depth-first matters:* every `pandoc-ast` document's root child is a single
`Div` wrapper, so a search over direct children finds no headers at all. I got
this wrong on my first pass and measured "1 of 24".

**Sessions carry real time and real counts:**

| session | turns | tool calls | conversation ran | imported |
|---|---|---|---|---|
| `2e9cd256` | 1110 | 320 | 2026-08-25 16:13 → 08-27 14:35 | 08-27 |
| `2e9cd256` | 1166 | 334 | 2026-08-25 16:13 → 08-28 10:56 | 08-28 |
| `cdb16054` | 44 | 14 | 2026-08-28 15:45 → 08-28 15:52 | 08-28 |
| `cdb16054` | 171 | 53 | 2026-08-28 15:45 → 08-28 16:41 | 08-28 |
| `cdb16054` | 346 | 103 | 2026-08-28 15:45 → 08-30 15:11 | 08-30 |

Every turn carries a timestamp, so first and last are exact.

**Documents carry no time at all.** A `document` root's params are `meta`,
`pandoc_api_version`, `route`, `source` — and `meta` is **empty on all 24**, so
there is no title or date hiding in frontmatter. The only date reachable is the
`blob`'s `imported_at`, via the `derived_from` edge. That is when *you ingested
it*, not when you wrote it.

**Routes are lopsided:** `pandoc-ast` 23, `claude-code-transcript` 5,
`notes` 2.

**Five of the 29 rows are duplicate ingests** of two actual things — `2e9cd256`
twice and `cdb16054` three times. They are also the only cause of the ugly
filenames: a stem collision appends the 36-character root guid **to both**, so
`2e9cd256-….html` becomes `2e9cd256-…-2e9cd256-….html`.

## Settled

Answered 2026-09-01. Each entry is the decision and the reason it survived, not
the argument that got there.

**Light theme, forced.** The page inherits the system setting today and shows
dark. Drop to light only for now, keeping the colour tokens so flexible theming
is a later change rather than a rewrite.

**Q1 — display names come from a record, not from the file.** The heading-
derived title is **rejected**: a name that changes when the prose changes is a
reminder pretending to be an identifier, and reaching into the document to
surface one is exactly the implicitness this project avoids elsewhere.

Instead, a display name is its own **node**, connected to the root by an edge —
the shape `alias` already uses for legacy handles. Not stored *on* the root:
records are immutable and the root is not ours to edit. When v0.3.0 makes nodes
changeable this may become a property, and that is an explicitly transitional
position rather than an accident.

Two refinements found while checking it:

- **Do not reuse `alias`.** An alias answers *"what does this string resolve
  to"* — input to node. A display name answers *"what should I show for this
  node"* — node to string. Opposite directions, and overloading the type would
  have `compost lookup` resolving display names as handles.
- **Reading and writing split.** v0.2.10 teaches the view to *read* a display
  name when one exists and fall back to the filename when it does not. Nothing
  in this release *writes* one. Creation is a hand-written JSONL file under
  `graph/`, which `CLAUDE.md` already blesses — *"anything may write records;
  `check` is the gate"* — and a CLI surface for it stays forbidden, as
  `CLAUDE.md` says of `compost layer alias`.

So the index ships showing filenames, and improves for each document you choose
to name. That matches *"the file name is good enough right now"* without
closing the door.

**Q2 — sessions show a real range, documents show `imported`, and the word is
on the page.** Option (a). One is when a thing happened and the other is when it
was fed in, and one column called "date" would blur them.

**Q4 — both sections sort newest first.** Conversations by last turn, documents
by `imported_at` descending.

**Q5 — trimmed to what earns its place.**

| conversations | documents |
|---|---|
| start | display name (filename until named) |
| last turn | word count |
| session id | imported |
| source filename | |

Turn and tool-call counts are dropped. They still distinguish the duplicate
rows without them: the three `cdb16054` copies all start `2026-08-28 15:45` and
end `15:52`, `16:41` and `08-30 15:11`, so the range separates them on its own.

**Q6 — filtering is postponed**, and the thing actually wanted is recorded
instead: **full-text search across documents** — type words, the note surfaces.
That is a different feature from filtering a list of 29 rows, and building the
small one would not have led to the big one.

**Q7 — show all five duplicate rows.** Sorted newest-first, so the top one is
current. *"Let an unplanned thing cause trouble so we can fix it properly based
on real trouble."*

**A3 — the index moves into its own function. Internal only:** `compost render`
is called exactly as before, and no flag or argument changes.

## Settled — two sections, in the code's words

`Sessions` and `Documents`, literally the two strings in `records.ROOT_TYPES`,
capitalised. Not `Conversations`, not `Transcripts`, not `Notes`.

Three sections were asked for; the graph can tell apart two.
`records.ROOT_TYPES` is `{document, session}` and nothing else, and measured
today the three-way split leaves **23 of 29 rows homeless** and one section
empty:

| section | rows |
|---|---|
| transcripts — `session` roots | 5 |
| notes — `document`, route `notes` | 2 |
| conversations — `responds_to` chains | **0** |
| **no name yet** — `document`, route `pandoc-ast` | **23** |

("Conversations" is empty because the conversation loop has never run here. The
4,469 `replies_to` edges are turn threading *inside* a transcript — a different
relation.)

**The code's words are chosen deliberately, as an irritant.** *"Let the pain
make me think of a better solution."* A page that says `Documents: 23` in a word
nobody thinks in is a standing reminder that the vocabulary is unfinished, and
relabelling costs nothing once it is.

And the drift is not only between the human and the code: this document spent
six sections saying *conversations* while `render_all` says `session`. **Nobody
involved was using the code's vocabulary**, which is the strongest argument for
putting it on the page.

**The real fix is v0.3.0's artifact kinds.** ImTA, AoTA and TA are the three
categories actually wanted; `docs/design-0.3.0.md` §2 settles them as declared
at ingest and verified by `check`. When a root carries its kind, the sections
become the kinds.
